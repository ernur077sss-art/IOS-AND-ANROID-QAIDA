# Qayda Kazakhstan Qodex — моб версия

Мобильное приложение для открытия Казахстана и совместной организации поездок. Expo / React Native для iOS и Android; Next.js для приглашений и редакции; Supabase PostgreSQL/Auth для общих данных.

Статус: рабочая версия для закрытого тестирования, не опубликована в магазинах. Состояние всех согласованных этапов — [docs/PLAN.md](docs/PLAN.md). Проверки и ограничения — [docs/VERIFICATION.md](docs/VERIFICATION.md).

## Быстрый запуск

Требуется Node.js >=22.13 и npm. Все JS зависимости зафиксированы в package-lock.json.

```sh
npm ci
cp apps/web/.env.example apps/web/.env.local
cp apps/mobile/.env.example apps/mobile/.env.local
```

Заполните URL и **publishable key** нашего Supabase из [docs/ENVIRONMENTS.md](docs/ENVIRONMENTS.md). Service role в приложениях не используется. Без переменных окружения доступен явно помеченный read-only демокаталог; изменения не симулируются.

```sh
npm run dev
# Web: http://127.0.0.1:3002
npm run mobile -- --port 8087
```

Для Expo Go: из apps/mobile выполните `npx expo start --go --port 8087`. Для разработки ссылок используйте development build. На физическом телефоне localhost относится к самому телефону: задайте доступный адрес веб-приглашений и используйте LAN Metro.

## Нативная сборка

```sh
cd apps/mobile
npx expo run:ios
npx expo run:android
```

iOS требует Xcode и CocoaPods; Android — JDK и Android SDK. Нативные каталоги генерируются Expo и не хранятся в Git. Для локальной подписанной сборки симулятора платный Apple Developer аккаунт не нужен. Не отключайте signing у симулятора: SecureStore требует корректных entitlements.

На текущей машине Xcode доступен через `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`; системный xcode-select не изменялся. CocoaPods установлен локально в игнорируемый work/gems. Текущий отдельный симулятор — «Qayda Qodex — моб версия».

EAS профили лежат в apps/mobile/eas.json. Для распространения нужны собственные аккаунты, signing и согласование публикации.

## Структура

- apps/mobile: нативные экраны, общий provider состояния, UI и защищённое хранилище сессии.
- apps/web: адаптивный каталог, приглашения, комнаты и редакторский интерфейс.
- packages/domain: модели, денежная арифметика, даты, ICS и поиск.
- packages/api-client: единый контракт с Supabase RPC.
- supabase/migrations: воспроизводимые ограничения, RLS и транзакции.
- data/catalog.json: проверенные минимальные сведения; цены и сеансы не выдумываются.
- tests и scripts: доменные, PostgreSQL и браузерные проверки.

## База данных

Рабочее окружение изолировано от проекта Claude. Все команды должны указывать ref `evnqorvwppdjdznhbwip`. Не используйте `jqekaeothrlushnknohb`.

Схема уже применена в нашем проекте. При следующих изменениях добавляйте новую миграцию и применяйте её адресным скриптом:

```sh
npx supabase@2.121.0 login
node scripts/apply-migration.mjs supabase/migrations/НОВАЯ_МИГРАЦИЯ.sql
```

Скрипт фиксирует версию в private.schema_migrations и выполняет миграцию в транзакции. Это выбранный Management API workflow; **не запускайте обычный db push поверх этого окружения без согласования журнала миграций**.

Для чистого окружения применяются все SQL-файлы по порядку, начиная с 202610200001_core.sql, затем seed.sql. Скрипт намеренно привязан к ref нашего проекта; для другого окружения сначала явно измените guard и конфигурацию. Seed повторяемый: редакционные тексты не перезаписываются; обновляются только указанные метаданные происхождения.

Первого реального редактора назначает владелец БД после входа пользователя:

```sql
insert into private.admin_roles(user_id)
select id from auth.users where email = 'EMAIL_РЕДАКТОРА'
on conflict do nothing;
```

Пользователи не могут выдать эту роль себе. В закрытом тестовом окружении редактором назначен только синтетический owner; его пароль не хранится в Git и не показан в интерфейсе.

## Вход

Реализованы email sign-in link (PKCE) и ввод OTP, если шаблон письма содержит код. Стандартное письмо текущего Supabase содержит ссылку. Для web callback служит /auth/callback, для Expo — qayda://login. Разрешённые адреса задаются в supabase/config.toml; для production их нужно заменить/дополнить реальным доменом.

Для доставки писем произвольным пользователям требуется настроить собственный SMTP и проверить оба потока на реальных устройствах. Не считайте синтетические password-сессии из тестов проверкой доставки email.

Приглашение обрабатывается внутри страницы: секрет удаляется из URL и остаётся в памяти. Вход по email-коду не покидает страницу; при входе по ссылке вернитесь в исходную вкладку приглашения. После перезагрузки этой вкладки нужно снова открыть исходную ссылку. Секреты не сохраняются в localStorage.

## Проверки

```sh
npm run check
npm run test:e2e
cd apps/mobile && EXPO_NO_TELEMETRY=1 npx expo export --platform all
```

Базовые браузерные тесты самостоятельно запускают сервер на 3017 в демонстрационном режиме. Локально используется Chrome, в CI — Chromium из Playwright. `npm run test:db` запускает настоящие PostgreSQL функции/RLS в PGlite с pgcrypto; подменён только auth.uid() для разных ролей. Docker не нужен.

Облачная проверка выполняется отдельно на изолированных синтетических аккаунтах:

```sh
node scripts/prepare-cloud-test.mjs
# Применить сгенерированный work/provision-test-users.sql только в нашем тестовом проекте.
node scripts/cloud-smoke.mjs
QAYDA_TEST_URL=http://127.0.0.1:3002 QAYDA_CLOUD_E2E=1 npm run test:e2e
```

Пароли, токены, SQL с тестовыми credentials и browser traces находятся в игнорируемых каталогах. Не публикуйте их. Тестовые аккаунты и отменённые планы не являются реальными пользователями или traction.

## Границы версии

Нет денежных переводов, бронирования билетов, автоматической синхронизации календарей и выдуманного Ticketon API. Карта открывает внешний поиск по проверенному адресу/точке. Чат обновляется явно; история доступна страницами. Удаление аккаунта пока регистрирует запрос для администратора, а не обещает немедленное удаление.

Перед публичным запуском: SMTP, домен и Universal/App Links; физические iOS/Android проверки; проверка импорта ICS; лицензированные фотографии; полировка нативных форм; разбор транзитивных npm advisories; production инфраструктура и утверждённые тексты о данных/условиях. Seoul является тестовым регионом и не означает готовность обработки реальных персональных данных Казахстана.
